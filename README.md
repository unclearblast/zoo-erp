# 🦁 Zoo ERP System (SOLID-based)

## 1. Описание предметной области

Данный проект моделирует упрощённую ERP-систему для зоопарка.  
Система предназначена для автоматизации базовых процессов:

- учета животных разных видов;
- ухода за животными (кормление, уборка, лечение);
- проведения медицинского осмотра при приёме в зоопарк;
- формирования отчетной информации.

Основной акцент сделан не на полноту функционала, а на демонстрацию
грамотного архитектурного проектирования с применением принципов **SOLID**.

---

## 2. Архитектура системы

Система разделена на логические модули:

- `animals` — животные и их базовые характеристики;
- `care` — интерфейсы ухода за животными;
- `staff` — сотрудники зоопарка;
- `report` — отчетный модуль;
- `zoo` — агрегирующий объект зоопарка.

Такое разделение снижает связанность компонентов и упрощает расширение системы.

---

## 3. Реализация принципов SOLID

### 3.1 Single Responsibility Principle (SRP)

Каждый класс имеет **одну зону ответственности**:

- `Animal` — описание животного;
- `Keeper`, `Veterinarian` — выполнение конкретных обязанностей;
- `Zoo` — управление коллекцией животных;
- `ReportService` — генерация отчетов.

Изменение логики отчетов не затрагивает животных или сотрудников, и наоборот.

---

### 3.2 Open / Closed Principle (OCP)

Система **открыта для расширения, но закрыта для изменения**:

- новый вид животного добавляется через новый класс, реализующий `Animal`;
- новый тип сотрудника — через новый класс;
- новый формат отчета — через новую реализацию `ReportService`.

Существующий код при этом не изменяется.

---

### 3.3 Liskov Substitution Principle (LSP)

Любая реализация интерфейса `Animal` может использоваться в системе
без нарушения логики:

- методы кормления, лечения и отчетности работают с `Animal`,
  а не с конкретными классами (`Lion`, `Snake` и т.д.).

Это гарантирует корректную подстановку наследников.

---

### 3.4 Interface Segregation Principle (ISP)

Вместо одного «жирного» интерфейса используются узкоспециализированные:

- `Feedable` — кормление;
- `Cleanable` — уборка;
- `Healable` — лечение.

Сотрудники реализуют **только те интерфейсы, которые им действительно нужны**.
Например, смотритель не обязан лечить животных.

---

### 3.5 Dependency Inversion Principle (DIP)

Высокоуровневые модули не зависят от конкретных реализаций:

- класс `Zoo` зависит от абстракции `ReportService`,
  а не от конкретного способа вывода отчета.

Это позволяет легко заменить консольный отчет, например, на PDF или файл.

---

## 4. Возможные проблемы при расширении

- при усложнении логики кормления потребуется вынести правила в отдельный сервис;
- при добавлении состояний животных (карантин, болезнь) понадобится
  дополнительная модель состояния;
- при переходе к GUI потребуется новый слой представления.

Тем не менее, текущая архитектура минимизирует влияние таких изменений.

---

## 5. Обоснование введенных абстракций

Используемые абстракции:

- уменьшают связанность компонентов;
- упрощают тестирование;
- повышают читаемость кода;
- отражают реальную предметную область зоопарка.

Архитектура масштабируется линейно по сложности.
